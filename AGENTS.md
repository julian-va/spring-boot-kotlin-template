# AGENTS.md

Single-module Spring Boot 4.1.1 Kotlin template: Kotlin 2.3.21, Java 25, Gradle Kotlin DSL (`build.gradle.kts`). No CI, no linter/formatter, no LICENSE — don't look for or assume these exist.

## Commands

Always use the wrapper; a bare `gradle` resolves a different version on this machine.

- Build (compiles + tests): `./gradlew build`
- All tests: `./gradlew test`
- One test class: `./gradlew test --tests "jvacloud.spring_boot_kotlin_template.OpenApiDocumentationTests"`
- Run app: `./gradlew bootRun` — actuator at `/actuator/health`, OpenAPI at `/v3/api-docs`, Swagger UI at `/swagger-ui.html`. No `management.*` config exists yet.

## Coverage (JaCoCo)

- `./gradlew check` — and therefore `build` — runs `jacocoTestCoverageVerification` with an 80% instruction minimum, so adding a class without tests fails the build.
- **Two** application classes are excluded: `**/SpringBootKotlinTemplateApplication.class` and `**/SpringBootKotlinTemplateApplicationKt.class`. The second is the file facade Kotlin generates for the top-level `main`; without it the gate fails at 0% on the very first run.
- Data-only code is excluded too (see `jacocoExcludes`): DTOs under `infrastructure/entryPoints/**/dto`, JPA entities under `infrastructure/providers/jpa/entities`, `infrastructure/config`, and `domain/model/exception`.
- Kotlin code generation and the gate (verified empirically):
  - members generated by a `data class` (`copy`, `componentN`, `toString`, `equals`, `hashCode`) are filtered by JaCoCo and do not count;
  - the `$default` bridge generated by default arguments **is** counted, so a default nobody exercises shows up as uncovered;
  - every constructor `val` generates a getter that counts as uncovered until the property is read.
- The two application classes are still the only main classes, so the bundle is empty and the gate passes vacuously. It starts enforcing as soon as a **non-excluded** class exists.
- Report: `build/reports/jacoco/test/html/index.html` (HTML + XML, gitignored).

## Spring Boot 4 renamed these starters — don't "correct" them

Boot 3 / most examples online use names that are wrong here. This project verifiably builds with:

- `spring-boot-starter-webmvc` (not `spring-boot-starter-web`)
- `spring-boot-starter-webmvc-test` and `spring-boot-starter-actuator-test` (not `spring-boot-starter-test`)

Adding the Boot 3 names pulls in a duplicate legacy stack.

## Springdoc is pinned by hand

`springdoc-openapi-starter-webmvc-ui:3.1.1` is explicit because the Spring Boot BOM does not manage it, and the 2.x line targets Boot 3. Don't drop the version or "fix" it to 2.x. `OpenApiDocumentationTests` fails if `/v3/api-docs` stops responding, so a Boot upgrade that breaks springdoc surfaces as a test failure.

## Package name is intentionally odd

`jvacloud.spring_boot_kotlin_template` contains an underscore because Initializr rejected the hyphenated artifact name; `HELP.md` explains this but is untracked (listed in `.gitignore`). Renaming it touches the package, both source trees, `group`, and `settings.gradle.kts` — ask the user first instead of treating it as cleanup.

## Toolchain gotchas

- JDK 25 is pinned via `java.toolchain`. It must already be installed (SDKMAN `current` here); `settings.gradle.kts` has no foojay toolchain resolver, so Gradle fails the build rather than downloading a JDK.
- Kotlin 2.3.21 comes from the Gradle plugin; there is no separate Kotlin installation. `kotlin-reflect` and `tools.jackson.module:jackson-module-kotlin` are required because Boot 4 uses Jackson 3 — without them, Kotlin classes without a no-arg constructor do not deserialize.
- No annotation processors are wired. If one is needed, prefer KSP over kapt.
- Compiler flags: `-Xjsr305=strict` (JSR-305 nullability is honored) and `-Xannotation-default-target=param-property` (annotations without a use-site target apply to both the parameter and the property). For Bean Validation on constructor properties, `@field:` is still the reliable target.
- No Lombok. Don't add it: data classes, `val` and primary constructors replace it.
- `build.gradle.kts` is intentionally kept free of comments; don't add explanatory comments to it.

## Runtime config

- `spring.threads.virtual.enabled: true` in `application.yaml`: Tomcat serves requests on virtual threads. `ThreadLocal` state (including Spring Security's `SecurityContext`) is not inherited by work handed to another executor; propagate it explicitly with coroutines, `@Async` or custom executors.

## Skills

- Project skills live in `.opencode/skills/<id>/SKILL.md`. The directory name is the skill ID and the frontmatter needs a `description`, or OpenCode registers the skill but never advertises it.
- Validate skill frontmatter before committing. A `: ` (colon-space) inside an unquoted value is invalid YAML: GitHub rejects the whole file with "mapping values are not allowed in this context", while OpenCode's lenient parser accepts it, so the mistake passes locally and only fails on GitHub.
- Available skills: `kotlin-backend` (architecture, Kotlin and Spring conventions) and `security` (OWASP, Spring Security 7, secrets, supply chain).
